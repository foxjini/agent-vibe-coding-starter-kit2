01

큰 그림 — 다섯 조각이 어떻게 붙어 있나

각 조각은 자기 옆 조각하고만 이야기합니다. 프론트엔드는 라즈베리파이를 모르고, 라즈베리파이도 프론트엔드를 모릅니다. 가운데의 백엔드가 전부 중계합니다.

조각기술어디서 돌아가나맡은 일

02

이것 하나만 이해하면 절반은 끝납니다

desired_state(되어야 하는 상태)와 current_state(지금 실제 상태). 이 두 칸이 시스템 전체의 심장입니다.

학생이 화면에서 「도어락 열기」를 눌렀다고 해서 백엔드가 라즈베리파이에게 전화를 걸지 않습니다. 대신 데이터베이스에 “도어락은 열려 있어야 한다”고 적어 둡니다. 라즈베리파이는 2~5초마다 스스로 백엔드에 물어봅니다. “내가 어떤 상태가 되어야 하지?” 그리고 그대로 하고, 결과를 보고합니다.

시점desired_statecurrent_state무슨 일이 벌어졌나
평소lockedlocked둘이 같음 = 할 일 없음
PIN 인증 직후unlockedlocked백엔드가 목표만 바꿈. 아직 문은 잠겨 있음
파이가 폴링한 뒤unlockedunlocked파이가 GPIO를 움직이고 결과를 보고함
왜 이렇게 만드나

파이가 잠깐 꺼져 있거나 Wi-Fi가 끊겨도 “열려야 한다”는 사실이 DB에 남아 있습니다. 파이가 다시 켜지면 폴링해서 따라잡습니다. 백엔드가 직접 명령하는 방식이었다면 그 명령은 허공에 사라집니다.

그래서 백엔드는 파이의 IP 주소를 몰라도 됩니다. 항상 파이가 먼저 찾아옵니다.

개발 중에는 파이가 없다

2차 개발 전반부에는 실기기 대신 Mock 프로바이더가 파이 역할을 대신합니다 (backend/iot/mock_provider.py). 목표 상태를 적는 즉시 실제 상태도 같이 바꿔 주므로 화면에서는 진짜처럼 보입니다. .env의 DEVICE_MODE가 mock인지 hardware인지가 이 갈림길입니다.

03

버튼 한 번을 끝까지 따라가기

학생이 키패드에 예약 PIN 6440을 누르고 확인을 눌렀습니다. 도어락이 열리기까지 코드가 지나가는 길 전체입니다. 이 순서가 곧 폴더 구조입니다.

  1. 화면에서 버튼을 누른다 frontend/components/booth/VirtualBoothSimulator.tsx

    키패드 컴포넌트가 입력한 4자리를 모아 부모에게 넘깁니다.

  2. 부모 페이지가 서버에 요청을 보낸다 frontend/app/page.tsx → handleVerifyPin()

    POST /api/booth/verify-keypad 에 { pin: "6440" }을 보냅니다. 주소는 utils/apiConfig.ts가 .env를 보고 만들어 줍니다.

  3. 백엔드 라우터가 요청을 받는다 backend/routers/reservations.py → verify_keypad()

    라우터는 받아서 넘기는 일만 합니다. 판단은 하지 않습니다.

  4. Pydantic이 형식을 먼저 검사한다 backend/schemas/reservation.py → KeypadVerifyRequest

    4자리가 아니면 여기서 422로 잘립니다. 서비스 코드까지 가지 않습니다.

  5. 서비스가 규칙을 판단한다 backend/services/booth_service.py → verify_and_trigger()

    관리자 PIN인가? 아니면 예약 PIN인가? “무엇을 할지” 정하는 곳이 여기입니다.

  6. DB에서 예약을 찾는다 backend/db/database.py → get_reservation_by_pin()

    status='reserved'인 예약만 찾습니다. 이미 쓴 PIN은 'active'라 여기서 안 나옵니다 — 이것이 PIN 일회성이 동작하는 방식입니다.

  7. 예약을 사용 완료로 표시한다 database.py → update_reservation_status(id, 'active')

    이 한 줄 때문에 같은 PIN을 두 번 쓸 수 없습니다.

  8. 기기의 목표 상태를 바꾼다 backend/iot/mock_provider.py → set_actuator_state()

    도어락 unlocked, 릴레이 on, LED on. 02번에서 본 desired_state가 여기서 바뀝니다. 동시에 control_log에도 기록됩니다.

  9. 열려 있는 모든 브라우저에 방송한다 backend/websocket_manager.py → broadcast()

    {"type": "device_state", ...}를 WebSocket으로 뿌립니다. 화면이 새로고침 없이 바뀌는 이유가 이것입니다.

  10. 화면이 방송을 받아 다시 그린다 frontend/hooks/useKaraokeSocket.ts → page.tsx

    도어락 카드가 초록색 UNLOCKED로 바뀝니다.

  11. 라즈베리파이가 폴링해서 따라잡는다 pi/ → GET /api/v1/devices/door_lock_1/desired-state

    목표가 unlocked인 걸 보고 GPIO를 움직인 뒤, POST /api/v1/devices/door_lock_1/state로 결과를 보고합니다. 그때 실제로 문이 열립니다.

기억할 한 문장

라우터는 받고, 서비스는 판단하고, DB는 저장하고, WebSocket은 알린다. 새 기능을 만들 때도 이 네 자리에 나눠 넣으면 됩니다.

인증 세 종류 — 헷갈리기 쉬운 곳

기기용

파이와 비전 클라이언트가 씁니다. .env의 같은 키를 서로 맞춰 두면 통과.

verify_device_api_key()

일반

예약·노래 조회는 누구나 됩니다. 관람객이 바로 써야 하니까요.

verify_user_auth()

관리자

도어락·전원 제어와 강제 종료. PIN으로 토큰을 받아 X-Admin-Token으로 보냅니다.

verify_admin_token()
여기를 조심

기기를 직접 제어하는 API에 관리자 인증을 빼면 관람객이 도어락을 열 수 있습니다. 새 제어 API를 만들 때는 반드시 _admin: str = Depends(verify_admin_token)을 붙이세요.

새 API를 하나 추가하려면

  1. schemas/에 요청 형식을 만든다 (필요할 때만)
  2. routers/의 알맞은 파일에 함수를 추가하고 @router.post("/경로")를 붙인다
  3. 판단이 필요하면 services/에, 저장이 필요하면 db/database.py에 함수를 만들어 부른다
  4. 화면이 바로 알아야 하면 ws_manager.broadcast()로 방송한다

http://localhost:8000/docs에 들어가면 만든 API를 브라우저에서 바로 눌러 볼 수 있습니다. 프론트엔드를 만들기 전에 여기서 먼저 확인하세요.

데이터베이스

표 여섯 개뿐입니다. 그중 devices가 중심입니다.

테이블한 줄에 무엇이 들어가나언제 늘어나나
devices기기 1대의 현재/목표 상태늘지 않음 — 6줄 고정, 값만 바뀜

devices 테이블이 왜 특별한가

6줄이 끝입니다 — door_lock_1, relay_1, led_1, speaker_1, keypad_1, pir_1. 새 기기를 추가하지 않는 한 줄 수는 그대로고 상태 칸만 계속 바뀝니다. 시스템 전체가 이 6줄을 보고 움직인다고 생각하면 됩니다.

예약 한 건의 일생

reserved — PIN 인증 성공 → active — 이용 종료 → completed

PIN은 reserved일 때만 통합니다. 인증되는 순간 active가 되어 같은 PIN이 두 번 통하지 않습니다. completed로 옮기는 일은 아직 사람이 해야 합니다 — 2차 개발의 스케줄러가 맡을 몫입니다.

MariaDB와 Supabase, 뭘 쓰나

지금 내 노트북

XAMPP의 MariaDB. .env에 DATABASE_URL이 없으면 이쪽으로 붙습니다. 스키마는 init.sql을 Workbench에 붙여넣어 실행합니다.

전시 Supabase

.env에 DATABASE_URL을 넣으면 자동으로 PostgreSQL로 바뀝니다. 스키마는 init_supabase.sql을 Supabase SQL Editor에서 실행합니다.

코드는 한 벌만 씁니다. 두 데이터베이스의 문법이 다른 부분(중복 시 갱신, 새 id 받기)은 database.py가 알아서 나눠 처리하므로, 여러분이 SQL을 두 벌 쓸 일은 없습니다.

데이터가 흐르는 방향

page.tsx가 서버에서 받아온 기기·예약·노래 목록을 전부 들고 있습니다. 각 탭 컴포넌트는 그것을 받아서 보여주기만 합니다. 값을 바꿔야 할 때는 page.tsx가 준 함수를 부릅니다.

왜 한 곳에 몰아 뒀나

예약 탭에서 예약을 만들면 시뮬레이터 탭의 키패드도 그 PIN을 알아야 합니다. 데이터를 각 탭이 따로 들고 있으면 서로 어긋납니다. 지금 규모에서는 한 곳에 모으는 편이 훨씬 안전합니다.

화면이 저절로 갱신되는 이유

useKaraokeSocket이 백엔드와 WebSocket을 계속 열어 둡니다. 백엔드가 방송하면 page.tsx의 handleWsMessage가 받아 처리합니다.

booth_auth키패드에 인증 성공/실패가 뜸
booth_event상단 안내 문구가 바뀜 (입장·종료 등)
reservation_created예약 목록을 다시 불러옴
song_recorded애창곡 목록을 다시 불러옴
주소를 코드에 직접 쓰지 마세요

fetch("http://localhost:8000/...")처럼 쓰면 Vercel에 올렸을 때 브라우저가 자기 자신에게 요청을 보내 전부 실패합니다. 항상 apiUrl("/api/...")을 쓰세요. 관리자 전용 API라면 adminFetch()를 쓰면 토큰이 자동으로 붙습니다.

07

자주 막히는 곳

증상을 먼저 찾고, 어디를 볼지 확인하세요.

상단 배지가 「연결 대기 중」에서 안 바뀝니다

백엔드가 안 떠 있거나 주소가 틀렸습니다. 순서대로 확인하세요.

① http://localhost:8000/health가 열리는가 → ② frontend/.env의 NEXT_PUBLIC_WS_URL이 맞는가 → ③ .env를 고쳤다면 프론트엔드를 껐다 켰는가

NEXT_PUBLIC_으로 시작하는 값은 서버를 다시 시작해야 반영됩니다.

브라우저 콘솔에 CORS 오류가 뜹니다

backend/.env의 CORS_ALLOW_ORIGINS에 지금 쓰는 프론트엔드 주소가 빠져 있습니다. 포트를 3000이 아닌 다른 값으로 띄웠다면 그 주소를 추가하세요.

고친 뒤에는 백엔드를 재시작해야 합니다.

한글이 «ë‹¤ì‹œ» 처럼 깨져 보입니다

DB에 넣을 때 이미 깨진 상태로 저장된 것입니다. 화면 문제가 아닙니다.

데이터베이스를 지우고 init.sql을 UTF-8로 다시 실행하세요. MySQL Workbench에 붙여넣어 실행하면 정상입니다.

기기 제어 버튼을 눌러도 아무 일이 없고 401이 뜹니다

정상 동작입니다. 기기 제어는 관리자 전용이 되었습니다.

첫 번째 탭 맨 위의 상자에 관리자 PIN을 넣어 인증하면 버튼이 살아납니다. PIN은 backend/.env의 ADMIN_PIN에 있습니다.

예약한 PIN을 넣었는데 «이미 사용한 비밀번호»라고 나옵니다

이것도 정상입니다. PIN은 한 번만 쓸 수 있습니다.

테스트하려면 예약을 새로 만들어 새 PIN을 받으세요. 또는 DB에서 그 예약의 status를 reserved로 되돌리면 다시 쓸 수 있습니다.

백엔드를 켜면 «Address already in use»가 뜹니다

이전에 켠 백엔드가 아직 살아 있습니다. 그 터미널 창에서 Ctrl+C로 끄거나, --port 8001처럼 다른 포트로 띄우세요.

포트를 바꿨다면 프론트엔드의 .env도 같이 바꿔야 합니다.

노래 탭만 비어 있습니다 (다른 탭은 정상)

데이터베이스가 안 떠 있을 가능성이 큽니다. 다른 탭은 값이 없어도 화면이 그려지지만 노래 목록은 전부 DB에서 옵니다.

XAMPP에서 MySQL이 Running인지 확인하고, 백엔드 터미널에 Failed to fetch songs 로그가 있는지 보세요.

어디부터 봐야 할지 모르겠습니다

백엔드 터미널을 먼저 보세요. 요청이 들어오면 한 줄씩 찍힙니다.

줄이 안 찍힌다 → 프론트엔드 문제 (주소·CORS). 줄은 찍히는데 500 → 백엔드 문제 (그 아래 빨간 글씨가 원인). 200인데 화면이 안 바뀐다 → 프론트엔드 표시 문제.
