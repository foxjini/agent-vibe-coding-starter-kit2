프론트엔드 만들기

AI 에이전트 없이, 웹 대화창 AI와 VS Code만으로 노래방 부스 프론트엔드를 고치고 기능을 더하는 방법입니다. 대화창 AI는 우리 파일을 볼 수 없습니다. 그래서 필요한 정보를 골라 한 번에 넣어 주는 일, 곧 컨텍스트 엔지니어링이 작업의 중심입니다. 그 일을 도구 두 개가 돕습니다.

01

왜 이 방식인가

대화창 AI가 아는 것은 내가 붙여 넣은 글뿐입니다. 무엇을 넣느냐가 답의 품질을 정합니다.

AI 에이전트 방식 (우리는 쓰지 않음)
  • AI가 저장소의 파일을 직접 열어 읽습니다
  • AI가 파일을 직접 고치고 명령도 실행합니다
  • .agents/rules는 이름만 대면 AI가 찾아 읽습니다
  • 틀리면 AI가 실행해 보고 스스로 고칩니다
대화창 방식 (우리가 쓰는 방식)
  • AI는 내가 붙여 넣은 글만 압니다. 파일 이름만 대면 모릅니다
  • 코드는 내가 VS Code에 붙여 넣습니다
  • 규칙도 내용을 넣어야 지킵니다 (도구가 넣어 줍니다)
  • 틀린 곳은 내가 ai:check와 눈으로 잡습니다

AI에게 “우리 프로젝트의 관리자 화면에 버튼을 달아 줘”라고만 쓰면, AI는 우리 화면을 본 적이 없으므로 그럴듯한 다른 프로젝트의 코드를 지어냅니다. 우리 폴더 구조, 색 이름, 백엔드 API, 기존 코드를 함께 주면 우리 코드에 맞는 답이 나옵니다. 이렇게 AI가 볼 글을 필요한 만큼, 정확하게, 순서대로 골라 넣는 일을 컨텍스트 엔지니어링이라고 합니다. 문장을 멋지게 쓰는 것보다 무엇을 넣느냐가 훨씬 중요합니다.

나이

AI 서비스마다 쓸 수 있는 나이와 조건(보호자 동의 등)이 다릅니다. 쓰기 전에 선생님과 함께 학교 지침과 서비스 이용 조건을 확인합니다. 이 매뉴얼은 특정 서비스를 정하지 않고, 어느 서비스에서나 되는 복사·붙여넣기만 씁니다.

비밀

.env 파일, API 키, 관리자 PIN, 장치 키(DEVICE_API_KEY), 실제 예약자 이름과 전화번호는 대화창에 넣지 않습니다. ai:context는 .env 파일을 거부하고 키처럼 생긴 글자를 [가림]으로 바꾸지만, 보내기 전 마지막 확인은 사람이 합니다.

03 대신

AGENTS.md의 “역할 지정 + rules/skills 참고” 문구와 03 핸드오버 가이드의 프론트엔드 프롬프트 틀은 파일을 직접 읽는 에이전트용입니다. 대화창에서는 이 문서의 도구가 규칙 원문과 파일 내용을 넣어 주므로, 프론트엔드 작업은 이 문서를 따릅니다.

02

작업 한 바퀴

아홉 걸음입니다. 색칠한 4번(계획 확인)과 8번(눈으로 확인)은 절대 건너뛰지 않습니다.

  1. 작업 카드 쓰기나

    하고 싶은 것 한두 문장과 눈으로 확인할 수 있는 완료 기준 두세 개. 넣을 파일은 파일 지도에서 고릅니다.

  2. 프롬프트 만들기도구

    npm run ai:context -- … → frontend/.ai/prompt.md 한 파일이 생깁니다.

  3. 붙여 넣고 보내기나

    VS Code로 prompt.md를 열고 Ctrl+A Ctrl+C → 새 대화에 붙여 넣고 보냅니다.

  4. 계획 확인AI → 나

    AI는 고칠 파일과 이유만 말하고 “진행할까요?”에서 멈춥니다. 파일 목록이 맞는지 보고 “진행”.

  5. 파일 전체 받기AI

    한 답변에 파일 하나, 전체가 옵니다. 파일이 더 있으면 붙여 넣은 뒤 “다음”.

  6. VS Code에 붙여 넣기나

    그 파일을 열고 Ctrl+A Ctrl+V Ctrl+S. 새 파일이면 만들어서 붙입니다.

  7. 점검도구

    npm run ai:check — 생략 흔적, 잘못 붙인 것, 타입 오류, ESLint를 봅니다.

  8. 눈으로 확인나

    npm run dev로 화면을 열고 완료 기준을 하나씩 직접 확인합니다.

  9. 커밋나

    git add 바꾼-파일 → git commit -m "무엇을 했는지". 다음 작업은 새 대화에서.

7에서 ❌

생략·붙여넣기 문제면 “생략 없이 파일 전체를 다시 줘” 또는 붙여 넣기를 다시 합니다. 타입·ESLint 오류면 ai:check가 알려 주는 --type bugfix --error .ai/last-error.txt 명령으로 2번부터 다시 합니다.

8에서 다름

오류는 없는데 화면이 기대와 다르면, 본 것(화면·콘솔·네트워크)을 .ai/evidence.txt에 그대로 적고 --type bugfix --evidence .ai/evidence.txt로 2번부터 다시 합니다.

한 바퀴를 대화로 보면

실습 3(새로고침해야 바뀌는 문 센서)을 대화로 옮긴 예시입니다. 실제 문장은 서비스마다 다릅니다. 볼 것은 원인 → 계획 → “진행할까요?”의 순서와 고칠 파일 목록입니다.

03

프롬프트 해부

ai:context가 만드는 프롬프트는 여섯 층입니다. 실습 3의 실제 프롬프트(42,647자)를 층별로 나눠 봤습니다.

카드규칙작업 카드관련 파일증거답변 형식

프롬프트의 70%가 파일입니다. 그래서 어떤 파일을 넣느냐가 가장 중요하고, 작업 카드는 짧아도 됩니다.

파일 고르는 요령

  • 고칠 파일은 반드시 넣습니다. 새 파일을 만들 때는 그 파일을 불러 쓸 파일(예: 패널을 붙일 app/admin/page.tsx)을 넣습니다.
  • 고칠 파일이 부르는 훅이나 유틸 중, 동작을 알아야 하는 것만 더합니다. 실시간 반영 문제면 hooks/useBoothData.ts가 그렇습니다.
  • .ts·.tsx를 넣으면 types/index.ts가 저절로 들어갑니다. 따로 적지 않습니다.
  • 보통 1~3개면 충분합니다. “혹시 몰라서” 큰 파일을 넣으면 답이 흐려지고 길이 한도에 걸립니다. 도구는 60,000자가 넘으면 경고합니다.

넣지 말 것

.env·키·PIN 실제 예약자 이름·전화번호 node_modules·.next 관련 없는 큰 파일 백엔드 코드 전체 지난 대화에서 받은 낡은 코드
카드 관리

화면·폴더·API가 바뀌면 프론트 담당이 frontend/scripts/ai/context-card.md를 직접 고칩니다. 카드가 틀리면 그 뒤의 모든 답이 틀립니다. 예를 들어 새 패널을 만들었으면 “폴더 지도”에 한 줄, 백엔드 담당이 새 API를 열었으면 “프론트가 부르는 API”에 한 줄을 더합니다.

05

도구 두 개

둘 다 frontend 폴더에서 실행합니다. 새로 설치할 것은 없습니다 (Node와 git만 있으면 됩니다).

npm run ai:context — 프롬프트 만들기

VS Code 터미널(Ctrl+`) · frontend 폴더 
cd frontend
npm run ai:context -- --type feature --task "대기열 패널에 예상 대기 시간을 보여 주고 싶어요" --done "대기 3명이면 '약 9분'이 보인다" --files components/admin/QueuePanel.tsx

npm run ai:context 바로 뒤의 --를 빼먹지 않습니다. 빠지면 npm이 옵션을 가져가 버립니다(도구가 알려 줍니다).

옵션뜻예
--type틀 고르기: feature 기능 추가 · bugfix 오류 고치기 · ui 화면 다듬기 · explain 설명 받기. 안 쓰면 feature--type bugfix
--task하고 싶은 것, 증상, 궁금한 점 (필수)--task "예약 목록에 오늘 날짜를 굵게"
--task-file--task 대신 파일에서 읽기. 글이 길거나 큰따옴표·$가 들어갈 때--task-file .ai/task.txt
--done완료 기준. 여러 번 씁니다. 눈으로 확인할 수 있게--done "375px 폭에서도 한 줄"
--files넣을 파일 (frontend 기준 경로, 여러 개, 필수)--files hooks/useBoothData.ts app/admin/page.tsx
--error오류 메시지를 담은 파일--error .ai/last-error.txt
--evidence화면·콘솔·네트워크에서 본 것을 적은 파일--evidence .ai/evidence.txt
--diff커밋 뒤로 지금까지 바꾼 내용(git diff)도 넣기--diff
--no-typestypes/index.ts 자동 포함 끄기 (길이를 줄일 때)
--out저장 위치. 기본 .ai/prompt.md
--help사용법 보기npm run ai:context -- --help

06

답변 형식 약속

모든 프롬프트 맨 끝에 붙는 여섯 가지입니다. 우리는 코드를 파일 전체를 지우고 붙여 넣는 방식으로 반영하기 때문에 이 약속이 필요합니다.

  1. 먼저 계획만 말하고 “진행할까요?”에서 멈춘다고칠 파일·새 파일 목록과 이유를 코드 없이 봅니다. 엉뚱한 파일을 고치려는 것을 코드 400줄을 받기 전에 잡습니다.어기면: 계획만 다시 말해 줘. 코드는 아직 쓰지 마.
  2. 코드는 한 답변에 파일 하나, 첫 줄부터 마지막 줄까지“3번째 함수 아래에 이걸 넣어”식 조각은 초보자가 넣을 자리를 틀리기 쉽습니다. 파일 전체면 Ctrl+A Ctrl+V 하나로 끝납니다.어기면: 바꾼 부분만 말고 이 파일 전체를 줘.
  3. 절대 생략하지 않는다// 기존 코드 동일을 그대로 붙여 넣으면 그 자리의 코드가 사라집니다. 바꾸지 않은 줄도, 주석도 그대로 다시 써야 합니다.어기면: 생략 없이 이 파일 전체를 첫 줄부터 마지막 줄까지 다시 줘.
  4. 400줄이 넘는 파일은 새 작은 파일로 빼고, 그래도 고치면 나눠서 준다긴 파일은 답이 끊기거나 생략되기 쉽습니다. 나눌 때는 // ===== 여기까지 (1/3) — 다음 조각에 이어짐 ===== 표시를 붙이고, JSX 안이 아닌 곳에서만 나눕니다.어기면: 이 파일은 400줄이 넘어. 새 작은 컴포넌트 파일로 빼는 방법으로 다시 계획해 줘.
  5. 붙인 파일에 없는 함수·API·패키지를 지어내지 않는다없는 API를 부르면 화면은 뜨는데 404가 납니다. 필요한 정보가 없으면 묻게 하고, 백엔드가 필요하면 “백엔드 담당에게 부탁할 내용”으로 따로 받습니다.어기면: 붙여 준 파일에 없는 함수나 API는 쓰지 말고, 있는 것만으로 다시 계획해 줘.
  6. 마지막에 확인 방법을 적는다실행할 명령과 화면에서 볼 것. 완료 기준과 맞는지 내가 비교합니다.어기면: 어떻게 확인하면 되는지 명령과 화면에서 볼 것을 알려 줘.

08

대화 관리

AI는 대화가 길어질수록 앞에서 준 규칙과 답변 형식을 잊습니다.

  • 작업 하나에 새 대화 하나. 지난 작업의 코드가 지금 파일과 섞이지 않게 합니다.
  • 같은 대화에서는 짧은 후속(“진행”, “다음”, 오류 붙이기)까지만 합니다. 파일을 붙여 넣은 뒤 새로 크게 물을 때는 최신 파일로 프롬프트를 다시 만듭니다. AI는 내가 붙여 넣은 뒤의 파일을 모릅니다. 지금까지 바꾼 것을 알려 주려면 --diff.
  • 생략이 나오기 시작하거나, 색 토큰·한국어 문구 같은 규칙을 어기기 시작하면 대화가 길어졌다는 신호입니다. 새 대화로 옮깁니다.
  • 답이 중간에 끊기면 “이어서”보다 나눠서 처음부터 다시 받는 쪽이 안전합니다. 이어 쓴 답은 어디서부터 이어졌는지 틀리기 쉽습니다.
  • 같은 질문에 답이 매번 조금씩 다른 것은 정상입니다. 그래서 계획 단계에서 방향을 정하고 갑니다.
