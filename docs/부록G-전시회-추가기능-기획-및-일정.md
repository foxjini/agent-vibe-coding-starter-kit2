## 1. 현재 진단 — 기능 개수가 아니라 "자동으로 도는 게 없다"

코드를 확인한 결과입니다. 추가 기능보다 **이것부터**입니다.

| 항목 | 상태 | 근거 |
|---|---|---|
| 예약 시간이 되면 자동 전원 ON/OFF | ❌ **없음** | 백엔드에 스케줄러가 없다. `/simulate-entry`, `/simulate-10min-warning`, `/simulate-end` 는 모두 사람이 눌러야 동작한다 |
| 라즈베리파이 실기기 데몬 | ❌ **없음** | `pi/main.py`가 없다 (`02_karaoke_daemon_mock.py`만 존재) |
| 노래 점수 저장 | ❌ **사라짐** | `song_history` 테이블에 score 컬럼이 없다. 곡명·가수·횟수만 남는다 |
| 관리자 운영 화면 | ❌ 없음 | 탭 5개가 모두 체험용. 선생님이 볼 화면이 없다 |
| 역할(관리자/학생) 구분 | 🔶 **부분 적용** | 관리자 인증 게이트와 API 보호는 적용 완료(§3-4). 화면 3분할(§3-2)은 ⑫에서 진행 |
| 관리자 마스터키 보호 | ✅ **해결** | 프론트에서 9179를 전부 제거하고 `.env`의 `ADMIN_PIN`으로 옮겼다 |
| 기기 제어 API 보호 | ✅ **해결** | 기기 제어·시나리오 강제 실행이 `X-Admin-Token`을 요구한다. 무인증 호출은 401 |
| 모바일 화면 | △ 미흡 | 레이아웃이 깨지진 않으나 제목이 두 줄로 잘리는 등 데스크톱용 |
| 중복 예약 차단 | ✅ 구현됨 | `reservations` 테이블 `UNIQUE KEY uq_date_slot` |
| PIN 일회성 | ✅ **해결** | 쓴 PIN은 `status='active'`가 되어 다시 조회되지 않는다. 개발용 만능 PIN(1234)도 `ALLOW_TEST_PIN`으로 차단 |
| Supabase(PostgreSQL) 연동 | ✅ **가능** | `DATABASE_URL`만 넣으면 전환된다. 스키마는 `backend/db/init_supabase.sql` |
| 노래방 영상·반주·채점 | ✅ 구현됨 | 부록F 참고 |

> 🚨 **가장 큰 구멍**: `AGENTS.md`에 팀이 직접 적은 **1번 트리거 규칙**이
> *"예약된 이용 시간에 따라 부스 전원과 장치를 자동 제어한다"* 인데 이게 수동입니다.
> 심사위원이 가장 먼저 확인할 항목입니다.

## 3. 화면 분리 설계 (역할별 3분할)

> 🖥️ **실제 작업 절차는 [`docs/부록J` 프론트엔드 화면 분리와 UI/UX 개선 작업서](부록J-프론트엔드-화면분리-및-UIUX-개선-매뉴얼.html)에 있습니다.**
> 이 장은 *왜·무엇을* 나누는지(설계), 부록J는 *어떻게* 나누는지(작업 순서와 코드 골격)입니다.

### 3-1. 왜 나눠야 하나 — UX가 아니라 보안 문제

지금은 학생·관람객이 보는 화면에 **부스를 망가뜨릴 수 있는 조작이 그대로 놓여 있습니다.**
전시 방식이 "관람객 직접 체험 + 실기기 반출"로 정해졌으므로 이건 취향 문제가 아닙니다.

| 노출된 조작 | 코드 위치 | 실기기 반출 시 실제로 벌어지는 일 |
|---|---|---|
| **관리자 마스터키 9179 "채우기" 버튼** | `VirtualBoothSimulator.tsx:466` | 비번이 화면과 소스에 그대로 — 누구나 관리자 인증 |
| 도어락 직접 잠금/해제 | `:521` | 관람객이 **부스 문을 연다** |
| 릴레이 전원 직접 ON/OFF | `:533` | 남이 노래 부르는 중에 **전원이 꺼진다** |
| 이용 종료 강제 실행 | `:459` | 남의 이용 시간을 강제 종료 |
| 종료 10분 전 강제 실행 | `:452` | 엉뚱한 타이밍에 LED 경고 |
| LED·스피커 직접 제어 | `:545`, `:557` | 조명·안내음 임의 조작 |

> ⚠️ **화면만 나누면 뚫립니다.**
> `POST /api/devices/{id}/control`은 `verify_user_auth`를 달고 있지만, 이 함수는
> **Supabase가 설정되지 않은 로컬 모드에서 무조건 통과**시킵니다.
> (헤더 없는 `curl`로 `/api/devices` 200 응답을 확인했습니다.)
> 버튼을 숨겨도 전시장 Wi-Fi에 붙은 폰에서 URL을 직접 호출하면 도어락이 열립니다.
> **화면 분리와 백엔드 보호는 반드시 세트로** 갑니다.

### 3-2. 3분할 구조

보는 사람과 기기가 셋으로 나뉘므로 2분할이 아니라 3분할입니다.

| 라우트 | 대상 | 기기 | 담을 것 |
|--------|------|------|---------|
| `/` | 학교 학생 | **폰** | 예약 신청, 부스 현황, 내 노래 기록, 미니게임 |
| `/try` | 전시장 관람객 | **폰** | 체험권 발급, 내 대기 번호, 내 차례일 때 입장 비밀번호 |
| `/booth` | 부스 이용자 | **대형 화면** | 도어 키패드, 노래방 영상·반주·채점, 랭킹, 어트랙트, 체험권 QR, 안내 음성·퇴실곡 |
| `/admin` | 선생님 | 노트북 | 기기 제어, 시나리오 강제 실행, 예약·통계, 대기열 운영, 강제 종료, 학생 대신 인증 |

> **`/booth` 는 부스 전원(릴레이)을 따라 화면이 바뀝니다.** 전원이 꺼져 있으면 키패드·QR·순위만 있는
> 대기 화면이고, 노래방을 여는 버튼이 없습니다. 비밀번호 인증으로 전원이 들어와야 환영 화면과
> [노래방 시작하기]가 나타납니다. 처음 만든 화면에는 [노래방 시작하기]가 늘 떠 있어서, 예약 없이도
> 노래방이 열리고 반주가 나왔습니다 — 예약제 부스라는 주제가 화면에서 무너지는 구멍이었습니다.

> 처음 기획에서는 관람객도 `/` 를 쓰기로 했지만, 만들어 보니 **예약이 있는 학생**과
> **예약이 없는 관람객**은 화면에서 해야 할 일이 전혀 달랐습니다. 한 화면에
> 둘 다 넣으면 둘 다 복잡해져서 `/try` 로 떼어 냈습니다.

Next.js App Router라 `app/booth/page.tsx`, `app/admin/page.tsx` 폴더만 만들면 되고,
기존 컴포넌트는 그대로 옮겨 붙입니다.

### 3-3. 현재 5개 탭 재배치

| 현재 탭 | 옮길 곳 |
|---------|---------|
| 가상 부스 관제 (기기 상태·직접 제어·시나리오) | **`/admin` 전부** (관람객에게 절대 노출 금지) |
| 키패드 시뮬레이터 | **`/booth` 대기 화면** — 비밀번호는 부스 앞에서 누르는 것이다. 실물 키패드와 같은 4x4 배치·동작 |
| 안내 음성·퇴실곡 | **`/booth`** — 소리는 부스에서 나야 한다 (처음에는 `/admin` 노트북에서 났다) |
| 노래방 예약 신청 & PIN 발급 | 신청은 `/` · 조회·[대신 입력]은 `/admin` |
| 실시간 노래방 반주 & 채점 | `/booth` (인증 뒤에만) |
| 나의 18번 & 노래 기록 | 보기만: 애창곡은 `/` · 전체 통계는 `/admin`. 기록은 부스에서 채점할 때 저절로 쌓인다 |
| 노래 퀴즈 미니게임 | `/` (대기열에서 기다릴 때 딱 맞다) |

### 3-4. 접근 통제는 어디까지

본격 로그인·회원가입은 §2의 "하지 말 것"에 그대로 둡니다(10주 일정에 맞지 않음).
대신 이 정도가 현실적인 절충입니다.

- [x] 관리자 PIN을 **백엔드가 검증** — 프론트 소스에서 9179 제거 ✅
- [x] 같은 검증을 `POST /api/devices/{id}/control` 과 `/api/booth/simulate-*` 에도 적용 ✅
- [x] 예약 신청·키패드 인증·노래 기록은 무인증 유지 (관람객이 바로 써야 하므로) ✅
  - 단, 노래 기록·점수 저장은 **부스 전원이 켜져 있을 때(인증된 이용 중)만** 받는다 — 아무 폰에서나
    순위와 애창곡 횟수를 꾸밀 수 없게 (`POST /api/songs`·`/api/scores` → 그 밖에는 409) ✅
- [x] 관리자 PIN은 코드가 아니라 `.env`로 뺀다 (`.agents/rules/security-rules.md`) ✅
- [ ] `/admin` 라우트 분리 — ⑫에서 진행 (2주차)

**동작 방식**

| 단계 | 내용 |
|------|------|
| 인증 | `POST /api/admin/login` 에 관리자 PIN → 단기 토큰 발급 (기본 1시간, `ADMIN_TOKEN_TTL_SEC`) |
| 사용 | 보호된 요청에 `X-Admin-Token` 헤더를 붙인다 (프론트는 `utils/adminSession.ts`가 자동 처리) |
| 해제 | `POST /api/admin/logout` 또는 브라우저 탭을 닫으면 만료 |
| 저장 | 토큰은 서버 메모리에만 둔다 — 백엔드를 재시작하면 모든 세션이 끊긴다 |

> ⚠️ 전시 전에 `.env`의 `ADMIN_PIN`을 **9179가 아닌 값으로 바꾸세요.**
> 기본값은 저장소와 `AGENTS.md`에 공개되어 있어 누구나 알 수 있습니다.
>
> ⚠️ `.env`의 `ALLOW_TEST_PIN`은 **반드시 `false`** 로 두세요.
> `true`면 예약하지 않은 사람도 만능 PIN(1234)으로 부스에 들어올 수 있습니다.

### 3-5. 부록G 기능과 라우트의 대응

새로 생긴 일이 아니라, **§2에 이미 잡아둔 기능을 그릇에 나눠 담는 것**입니다.

| 라우트 | 여기에 들어갈 §2 기능 |
|--------|------------------------|
| `/` | ③ 체험 모드 + ⑪ 모바일 화면 정리 |
| `/booth` | ⑥ 어트랙트 화면 + ④ 랭킹 표시 + 기존 노래방 |
| `/admin` | ⑧ 관리자 운영 대시보드 + ① 스케줄러 상태 확인 |

그래서 ⑫의 공수는 **라우트 분리 1.5일 + 접근 통제 1.5일 = 3일**입니다.
다만 **③⑥⑧보다 먼저** 해야 합니다. 나중에 하면 만들어 둔 화면을 다시 옮겨야 합니다.

### 3-6. 시연에서도 유리하다

한 화면에 다 있는 편이 시연에 좋아 보이지만, 실제로는
**폰(관람객) + 부스 대형 화면 + 관리자 노트북 3개를 동시에 보여주는 쪽**이 훨씬 강력합니다.
"역할별로 화면을 나눠 설계했다"는 것 자체가 정보통신과 프로젝트의 설명거리이고,
심사위원이 "학교에 실제로 도입 가능한가"를 판단할 때 바로 걸리는 지점입니다.

## 6. 🚨 안전 계획 (실기기 반출 + 불특정 다수 체험)

이 조합은 임팩트가 가장 크지만 **책임도 가장 큽니다.** 아래는 협상 대상이 아닙니다.

### 6-1. 전기 안전

- [ ] 릴레이가 제어하는 것은 **저전압(5V/12V) 기기만.** 220V 직결 금지
- [ ] 노출 배선 0 — 모든 배선은 기구물 안에 수납하고 관람객 손이 닿지 않게 한다
- [ ] 라즈베리파이·전원부는 **잠금 가능한 케이스**에 넣는다
- [ ] 멀티탭은 과부하 차단 기능이 있는 제품, 연장선은 통행로에 테이프 고정
- [ ] 배선 작업은 **전원 차단 상태 + 교사 입회** (로드맵 2단계와 동일)

### 6-2. 도어락 손끼임

- [ ] 솔레노이드 동작부에 **손가락이 들어가지 않는 가드**를 씌운다
- [ ] 도어락은 **실물 문이 아닌 데모 패널**에 장착 (사람이 갇힐 수 없게)
- [ ] "동작 중 손대지 마세요" 표지 부착

### 6-3. 관람객 위생·질서

- [ ] 마이크 **일회용 커버** 또는 매 체험 후 소독 티슈
- [ ] 1인 **3분 타이머 강제** (체험 모드 ③에 내장)
- [ ] 대기 줄 유도선, 안전요원 역할 1명 상시 배치

### 6-4. 소음

- [ ] 주변 부스 민원 대비 — 부스 방음재 또는 **헤드폰 모니터링 옵션**
- [ ] 전시 시작 전 주최 측에 음향 사용 사전 협의

### 6-5. 시스템 접근 통제

물리 안전만큼 중요합니다. 상세는 **§3-4**, 여기서는 전시 당일 최종 확인용입니다.

- [ ] 관람객 폰(`/`)에서 도어락·전원 제어 버튼이 **보이지 않는다**
- [ ] 프론트 소스에 관리자 비번 9179가 **남아 있지 않다**
- [ ] `curl`로 `POST /api/devices/door_lock_1/control`을 쳐 봤을 때 **거부된다**
- [ ] `/admin`은 선생님 노트북에서만 열어 두고, 자리를 비울 때 화면을 잠근다

## 7. ☁️ Supabase / Render / Vercel 배포 (전시 구성)

전시장에서는 관람객이 **자기 폰으로 직접 예약하고 이용**하므로 웹 계층을 클라우드에 올립니다.

```
[관람객 폰] --https--> [Vercel: 프론트] --https--> [Render: 백엔드] --> [Supabase: DB]
                                                          ^
                                        [라즈베리파이] ----+  (부스 안, 폴링)
```

### 7-1. 준비 순서

1. **Supabase** — 프로젝트를 만들고 SQL Editor에서 `backend/db/init_supabase.sql`을 한 번 실행
2. **Render** — `backend/` 배포. 환경변수에 아래를 넣는다
   | 키 | 값 |
   |---|---|
   | `DATABASE_URL` | Supabase의 **Connection pooling** URI (포트 6543) |
   | `ADMIN_PIN` | 9179가 **아닌** 새 값 |
   | `ALLOW_TEST_PIN` | `false` |
   | `DEVICE_API_KEY` | 라즈베리파이·비전과 동일한 값 |
   | `CORS_ALLOW_ORIGINS` | 배포된 Vercel 주소 |
3. **Vercel** — `frontend/` 배포. 환경변수 2개
   | 키 | 값 |
   |---|---|
   | `NEXT_PUBLIC_API_BASE_URL` | `https://[서비스].onrender.com` |
   | `NEXT_PUBLIC_WS_URL` | `wss://[서비스].onrender.com/ws` (HTTPS 페이지에서 `ws://`는 브라우저가 막는다) |
4. **라즈베리파이** — `pi/.env`의 `BACKEND_URL`을 Render 주소로 바꾸고 데몬 재시작

### 7-2. 코드는 이미 준비되어 있다

- `DATABASE_URL`이 있으면 백엔드가 **자동으로 PostgreSQL로 전환**된다 (로컬은 그대로 MariaDB)
- MySQL / PostgreSQL 양쪽에서 예약·PIN·노래 기록·관리자 인증이 동작하는 것을 확인했다
- ⚠️ `REQUIRE_USER_AUTH`는 `false`로 두세요. Supabase **Auth**를 실제로 붙이지 않은 상태에서
  켜면 대시보드 요청이 전부 401이 됩니다 (관람객은 로그인 없이 예약만 하므로 Auth는 불필요)

### 7-3. 🚨 그래도 부스 제어는 오프라인 대비가 필요하다

웹은 클라우드로 가더라도, **라즈베리파이가 Render에 못 닿으면 도어락이 열리지 않습니다.**
전시장 Wi-Fi는 믿을 수 없으므로 아래 중 하나를 반드시 준비하세요.

- [ ] **폰 핫스팟 또는 소형 공유기**를 예비로 가져가 파이·노트북을 붙인다
- [ ] 최악의 경우를 대비해 **노트북에서 백엔드를 로컬로 띄우는 절차**를 리허설에서 연습해 둔다
      (`pi/.env`의 `BACKEND_URL`만 노트북 IP로 바꾸면 된다)
- [ ] 유튜브 스트리밍이 끊길 때를 대비해 로컬 반주 파일을 준비한다 (부록F §4 ②③)

## 8. 🌐 로컬 폐쇄망 구성 (클라우드 장애 시 대안)

§7의 클라우드 구성이 기본이지만, 전시장 인터넷이 불안정하면 **부스 안에서
폐쇄망을 만들어 통째로 로컬로 돌릴 수 있어야** 합니다. 리허설 때 한 번 연습해 두세요.

**대안 구성 — 부스 안에서 폐쇄망을 만든다**

```
[노트북: 백엔드 + 프론트 + DB]  ←── 유선/전용 공유기 ──→  [라즈베리파이 5]
              ↑
              └── 전용 공유기 Wi-Fi ── [관람객 폰: QR 체험권·대기열]
```

- [ ] **소형 공유기를 직접 가져간다** (전시장 Wi-Fi에 의존하지 않는다)
- [ ] `pi/.env`의 `BACKEND_URL`을 공유기 내부 IP로 고정 (DHCP 고정 할당)
- [ ] 노트북 방화벽 8000 포트 인바운드 허용 확인
- [ ] **클라우드 배포본은 백업용으로만.** 현장 제어는 로컬로 돈다
- [ ] 유튜브 노래방 영상은 외부 인터넷이 필요하므로, **로컬 반주 파일을
      `public/media/karaoke/`에 미리 넣어 둔다** → 부록F §4 ②③ 경로
