대화창 AI로
라즈베리파이 만들기

AI 에이전트 없이, 웹 대화창 AI와 VS Code만으로 노래방 부스의 라즈베리파이 데몬에 부품을 더하고 오류를 고치는 방법입니다. 대화창 AI는 우리 파일도, 책상 위의 배선도 볼 수 없습니다. 그래서 코드·핀 배치·배선·오류를 골라 한 번에 넣어 주는 일, 곧 컨텍스트 엔지니어링이 작업의 중심입니다. 그 일을 파이썬 도구 두 개가 돕습니다.

01

왜 이 방식인가

대화창 AI가 아는 것은 내가 붙여 넣은 글뿐입니다. 라즈베리파이는 여기에 배선과 안전이 더해집니다.

아무것도 붙이지 않고 물으면
  • 라즈베리파이 5에서 동작하지 않는 RPi.GPIO 예제를 줍니다
  • 이미 도어락이 쓰는 GPIO17에 새 부품을 꽂으라고 합니다
  • 파이에 Flask 서버를 띄우는 등 우리 구조(파이가 묻는 폴링)와 다른 방식을 씁니다
  • 없는 API 주소와 기기 이름을 지어냅니다
context.py로 만든 프롬프트로 물으면
  • gpiozero·lgpio, 비어 있는 핀, 백엔드와의 약속이 프로젝트 카드로 들어갑니다
  • main.py와 booth_pins.py 원문이 들어가 기존 구조대로 고칩니다
  • 하드웨어 규칙(전원 끄고 배선, 가짜 핀 먼저, 안전 상태)이 함께 들어갑니다
  • 답은 계획부터, 파일 전체로, 생략 없이 옵니다

AI는 우리 저장소뿐 아니라 책상 위의 보드도 볼 수 없습니다. 어떤 부품을 어느 핀에 꽂았는지, 저항을 달았는지, 부품이 실제로 무엇을 했는지는 내가 글로 적어 줘야 압니다. AI가 준 코드는 도어락과 220V 릴레이를 움직이므로, 실기기에 올리기 전에 PC에서 가짜 핀으로 먼저 돌려 봅니다. 이 문서는 그 순서를 도구와 함께 정리했습니다. 프론트엔드 담당용 06 매뉴얼과 같은 방식이고, 파이에 맞게 도구와 규칙이 다릅니다.

안전

배선은 파이 전원을 뽑은 상태에서만 바꿉니다. 실기기 첫 연결과 220V 연결은 선생님 입회 아래, 배선 자가진단이 통과한 뒤에 합니다. 솔레노이드 도어락은 12V 별도 전원을 쓰고, 파이의 5V 핀에서 끌어오지 않습니다. AI의 답이 이와 다르면 AI가 틀린 것입니다.

비밀

pi/.env, DEVICE_API_KEY, Wi-Fi 비밀번호, 파이 로그인 비밀번호는 대화창에 넣지 않습니다. context.py는 .env 파일을 거부하고 키처럼 생긴 글자를 [가림]으로 바꿉니다. 오류 글 속 경로의 컴퓨터 사용자 이름도 ~로 바꿉니다.

나이

AI 서비스마다 쓸 수 있는 나이와 조건이 다릅니다. 쓰기 전에 선생님과 함께 학교 지침과 서비스 이용 조건을 확인합니다. AGENTS.md의 “역할 지정 + rules/skills 참고” 문구는 파일을 직접 읽는 에이전트용이고, 대화창에서는 이 문서의 도구가 규칙 원문을 넣어 줍니다.

02

어디서 고치고, 어디서 돌리나

코드는 PC에서 고치고 가짜 핀으로 확인합니다. 확인된 코드만 git으로 라즈베리파이에 옮깁니다.

PC (Windows)
  • 대화창 AI · VS Code
  • context.py → 붙여넣기 → check.py
  • 가짜 핀으로 main.py 실행, 관리자 화면 확인
  • git commit → git push
→
GitHub
  • 팀 저장소의 작업 가지
  • “가짜 핀에서 확인된 코드”만 올라옵니다
→
라즈베리파이 5
  • PC에서 ssh로 접속
  • git pull → 전원 뽑고 배선 → 선생님 확인
  • python test_hardware_gpio.py → python main.py

왜 PC에서 고치나

  • 대화창 AI, VS Code, 복사·붙여넣기가 모두 PC에 있습니다. SSH 창의 nano에 수백 줄을 붙여 넣으면 들여쓰기가 깨지기 쉽습니다.
  • 하드웨어 규칙 3번 “실기기 전에 Mock으로 먼저”를 PC에서 지킬 수 있습니다. gpiozero의 가짜 핀(mock)은 Windows에서도 돕니다.
  • git을 거치면 파이에 무엇이 들어갔는지 기록이 남고, 잘못되면 되돌릴 수 있습니다.
PC PowerShell · 처음 한 번 (pi 폴더) 
cd pi
python -m venv venv
venv\Scripts\activate
pip install gpiozero requests python-dotenv
copy .env.example .env

PC의 pi/.env에는 BACKEND_URL=http://127.0.0.1:8000(백엔드가 같은 PC일 때)과 backend/.env와 같은 DEVICE_API_KEY를 넣습니다. 파이의 가상환경은 부록I대로 --system-site-packages로 만듭니다.

다른 방법

VS Code의 Remote - SSH 확장을 쓰면 PC의 VS Code에서 파이의 파일을 바로 열어 붙여 넣을 수 있습니다. 이때 check.py와 가짜 핀 실행은 파이의 터미널에서 합니다 (GPIOZERO_PIN_FACTORY=mock python main.py). 어느 방법이든 “붙여 넣기 → 점검 → 가짜 핀 → 실기기” 순서는 같습니다.

03

작업 한 바퀴

열 걸음입니다. 색칠한 4번(계획 확인), 8번(가짜 핀으로 확인), 10번(선생님과 실기기)은 건너뛰지 않습니다.

  1. 작업 카드 쓰기나

    하고 싶은 것과 눈으로 확인할 완료 기준. 새 부품이면 --type wiring으로 배선표부터 받습니다.

  2. 프롬프트 만들기도구

    python scripts/ai/context.py … → pi/.ai/prompt.md. 파이썬 파일을 넣으면 booth_pins.py가 함께 들어갑니다.

  3. 붙여 넣고 보내기나

    VS Code로 prompt.md를 열고 Ctrl+A Ctrl+C → 새 대화에 붙여 넣고 보냅니다.

  4. 계획 확인AI → 나

    고칠 파일, 배선표, 안전 상태 처리를 봅니다. 핀이 겹치지 않고 RPi.GPIO가 없으면 “진행”.

  5. 파일 전체 받기AI

    한 답변에 파일 하나. main.py처럼 큰 파일은 (1/2) (2/2)로 옵니다. 붙여 넣은 뒤 “다음”.

  6. VS Code에 붙여 넣기나

    그 파일을 열고 Ctrl+A Ctrl+V Ctrl+S. 조각은 맨 끝에 이어 붙입니다.

  7. 점검도구

    python scripts/ai/check.py — 생략, 들여쓰기, 이름 오타, 핀 겹침, 가짜 핀으로 부품 만들어 보기.

  8. 가짜 핀으로 확인나

    백엔드를 켜고 가짜 핀으로 main.py를 돌려 터미널 출력과 관리자 화면을 봅니다.

  9. 커밋·파이로 옮기기나

    pi 파일만 git add → 커밋 → git push → 파이에서 git pull.

  10. 실기기 확인나 + 선생님

    전원을 뽑고 배선 → 선생님 확인 → test_hardware_gpio.py → main.py. 부품이 한 일을 눈으로 봅니다.

7에서 ❌

생략·붙여넣기면 “생략 없이 파일 전체를 다시 줘”. 문법·이름·가짜 핀 오류면 check.py가 알려 주는 --type bugfix --error .ai/last-error.txt 명령으로 2번부터.

8·10에서 다름

오류는 없는데 부품이 다르게 움직이면, 터미널 출력과 부품이 실제로 한 일, 실제 배선을 .ai/evidence.txt에 적고 --type bugfix --evidence .ai/evidence.txt로 2번부터.

04

프롬프트 해부

context.py가 만드는 프롬프트는 여섯 층입니다. 실습 4의 실제 프롬프트(36,399자)를 층별로 나눠 봤습니다.

카드규칙작업 카드관련 파일증거답변 형식

파일이 64%이고, 프로젝트 카드가 프론트엔드보다 큽니다(18%). 핀 배치표, 비어 있는 핀, 백엔드와의 약속, 안전 규칙처럼 코드만 봐서는 모르는 것이 카드에 들어 있기 때문입니다.

배선도 컨텍스트입니다

AI는 보드를 볼 수 없으므로 아래를 --task나 증거 파일에 글로 적습니다. 실습 4의 과제 글에 배선을 적은 이유입니다.

  • 부품의 모델명과 모듈에 적힌 핀 이름 (예: MC-38 리드 스위치, 부저 모듈 VCC·GND·S)
  • 실제로 꽂은 물리 핀 번호와 BCM 번호, 저항 값과 위치, 전원 전압(3.3V·5V·12V)
  • 부품이 실제로 한 일 (예: “문을 닫았는데 터미널에 ‘문이 열렸습니다’가 찍혔다”, “릴레이 LED는 켜지는데 딸깍 소리가 없다”)

넣지 말 것

pi/.env·장치 키 Wi-Fi·파이 로그인 비밀번호 venv·__pycache__ 관련 없는 스크립트 백엔드 코드 전체 지난 대화에서 받은 낡은 코드
카드 관리

핀을 새로 쓰거나 파일·API가 바뀌면 파이 담당이 pi/scripts/ai/context-card.md의 핀 배치표와 “비어 있는 BCM”을 직접 고칩니다. 카드가 틀리면 AI가 이미 쓰는 핀을 비어 있다고 믿습니다.

도구가 막아 주는 것

  • .env 파일은 넣지 않습니다 (.env.example은 됩니다). pi 밖의 파일, venv·__pycache__도 넣지 않습니다.
  • 키·토큰처럼 생긴 글자, DEVICE_API_KEY=값 줄, 데몬이 찍는 “출입증(API키)” 앞 글자를 [가림]으로 바꿉니다.
  • 오류 글 속 C:\Users\이름, /home/이름을 ~로 바꿉니다.
  • 400줄이 넘는 파일에 “큰 파일” 표시를 달아 AI가 나눠 주게 합니다. 60,000자가 넘으면 경고합니다.

틀 네 가지 (--type)

wiring

배선 계획

코드 없이 배선표만. 부품 핀 → 물리 핀·BCM, 저항·전원, 연결 순서, 확인 방법, 선생님과 할 단계. 새 부품은 이것부터.

feature

기능 추가

핀은 booth_pins.py에만, 새 액추에이터는 안전 상태에, RPi.GPIO·새 패키지 금지, 없는 API는 “백엔드 담당에게 부탁할 내용”으로.

bugfix

오류 고치기

원인 먼저, 그리고 코드·배선·설정·백엔드 중 어디 탓인지 가르기. .env 값은 묻지 않고 비교할 두 값만 알려 줍니다.

explain

설명 받기

코드를 고치지 않고 줄 번호와 함께 설명만. 폴링, 풀업 같은 말은 한 줄로 풀어 줍니다.

check.py — 붙여 넣은 뒤 점검

코드를 고치지는 않습니다. git이 아는 마지막 커밋과 비교해 pi 폴더에서 바뀐 파일을 살핍니다.

  • 바뀐 파일과 늘어난·지워진 줄 수. 생각보다 많이 지워졌으면 경고합니다
  • 생략 흔적(# ..., “기존 코드와 동일”, “나머지 그대로”, ...만 있는 줄)과 잘못 붙인 것(```, ### 파일:, 줄 번호), 조각 순서
  • 파이썬 문법·들여쓰기(IndentationError, 탭), 어디에도 없는 이름(실행하면 NameError가 날 오타·빠진 import)
  • 라즈베리파이 규칙: RPi.GPIO 사용, 코드에 바로 적은 핀 번호, 코드에 적은 장치 키, main.py에 고정된 'mock'

07

답변 형식 약속

모든 프롬프트 맨 끝에 붙는 여섯 가지입니다(wiring·explain은 코드가 없는 짧은 형식). 파이썬은 들여쓰기 한 칸이 동작을 바꾸므로 파일 전체를 받습니다.

  1. 먼저 계획만, 배선이 바뀌면 배선표도, 그리고 “진행할까요?”에서 멈춘다고칠 파일과 핀을 코드 500줄을 받기 전에 봅니다. 이미 쓰는 핀, 빠진 안전 상태를 여기서 잡습니다.어기면: 계획만 다시 말해 줘. 코드는 아직 쓰지 마.
  2. 코드는 한 답변에 파일 하나, 첫 줄부터 마지막 줄까지“이 함수 아래에 넣어”식 조각은 들여쓰기 깊이를 틀리기 쉽습니다. 파일 전체면 Ctrl+A Ctrl+V 하나로 끝납니다.어기면: 바꾼 부분만 말고 이 파일 전체를 줘.
  3. 절대 생략하지 않고, 스페이스 4칸으로 들여쓴다# 기존 코드 동일을 그대로 붙이면 그 메서드가 사라지고, 실행 중에 그 부품을 쓰는 순간 멈춥니다.어기면: 생략 없이 이 파일 전체를 첫 줄부터 마지막 줄까지 다시 줘.
  4. 400줄이 넘는 파일은 나눠 준다main.py(505줄)는 한 번에 받으면 끊기거나 생략되기 쉽습니다. # ===== 여기까지 (1/2) — 다음 조각에 이어짐 ===== 표시를 붙이고, 함수나 클래스가 끝난 자리에서만 나눕니다.어기면: main.py 를 (1/2), (2/2)로 나눠서 처음부터 다시 줘. 함수나 클래스가 끝난 자리에서 나눠 줘.
  5. 없는 것을 지어내지 않는다 — 핀은 booth_pins.py에, 비밀은 .env에없는 기기 id는 404, RPi.GPIO는 Pi 5에서 동작하지 않습니다. 새 pip 패키지는 파이에 설치가 안 될 수 있습니다.어기면: RPi.GPIO 말고 gpiozero 로, 핀 번호는 booth_pins.py 에만 두고 다시 계획해 줘.
  6. 확인 방법: 가짜 핀 명령 → check.py → 실기기 순서PC에서 무엇을 보면 되는지, 파이에서 선생님과 무엇을 확인할지 압니다.어기면: 가짜 핀으로 확인하는 명령과 터미널에 찍혀야 할 줄, 실기기 확인 순서를 알려 줘.

09

대화 관리

AI는 대화가 길어질수록 앞에서 준 규칙과 답변 형식을 잊습니다.

  • 작업 하나에 새 대화 하나. 배선표를 받은 대화와 코드를 받는 대화도 나눕니다. 배선표의 결론(고른 핀)은 다음 프롬프트의 --task에 적습니다.
  • 파일을 붙여 넣은 뒤 다시 크게 물을 때는 최신 파일로 프롬프트를 다시 만듭니다. 지금까지 바꾼 것을 알려 주려면 --diff.
  • 생략이 나오거나 RPi.GPIO가 다시 나오면 대화가 길어졌다는 신호입니다. 새 대화로 옮깁니다.
  • 서비스마다 길이 한도와 첨부 방식이 다릅니다. 긴 글이 첨부 파일로 바뀌어도 괜찮고, prompt.md 하나를 첨부해도 됩니다. 저장소 파일을 낱개로 여러 개 올리지는 않습니다.
