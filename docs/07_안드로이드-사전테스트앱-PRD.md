# 07. 안드로이드 사전 테스트 앱 PRD

> **문서 성격**: 제품 요구사항 정의서 (개발 착수용)
> **작성 목적**: 팀의 Flutter 앱을 만들기 전에, **백엔드·ATM 연동이 실제 스마트폰에서
> 동작하는지 먼저 확인**할 안드로이드 앱의 요구사항을 정한다
> **만드는 사람**: 지도교사 (팀 학생이 아님)
> **버전**: 1.0 · 2026-09-20

---

## 1. 왜 만드는가

팀의 최종 결과물은 **Flutter 네이티브 앱**입니다. 그런데 Flutter 담당 학생이
앱을 만드는 동안, 아래 질문들은 아무도 대답하지 못한 상태로 남습니다.

- 실제 스마트폰에서 백엔드 API가 그대로 붙는가? (지금까지는 PC 브라우저로만 확인)
- 스피커폰 받아쓰기로 만든 텍스트가 **규칙 엔진에 제대로 걸리는가?**
- 앱이 만든 QR을 **라즈베리파이 카메라가 실제로 읽는가?**
- 전시장 무선 환경에서 이 왕복이 몇 초 걸리는가?

이 앱은 그 질문들에 **먼저 답을 내는 도구**입니다. 여기서 확인된 계약과 함정을
Flutter 담당 학생에게 넘기면, 그 학생은 "되는지 안 되는지"가 아니라 "어떻게
예쁘게 만들지"에만 집중할 수 있습니다.

### 이 앱이 아닌 것

| | |
|---|---|
| ❌ 전시회에서 관람객에게 보여줄 앱 | 그건 Flutter 앱의 몫입니다 |
| ❌ 배포(구글 플레이)할 앱 | APK를 직접 설치해서 씁니다 |
| ❌ 예쁜 앱 | 기본 위젯만 씁니다. 꾸미는 데 시간을 쓰지 않습니다 |
| ❌ 오래 유지할 앱 | Flutter 앱이 완성되면 역할이 끝납니다 |

## 2. 성공 기준

아래 네 가지가 **전부** 확인되면 이 앱은 제 역할을 다한 것입니다.

| # | 기준 | 확인 방법 |
|---|---|---|
| S1 | 실제 안드로이드 폰에서 로그인하고 분석 결과를 받는다 | 화면에 위험 등급과 점수가 뜬다 |
| S2 | 문자 공유로 받은 텍스트가 **DANGER 100점**으로 판정된다 | 보이스피싱 문자를 공유 → 100점 |
| S3 | 스피커폰 받아쓰기 텍스트가 **DANGER로 판정된다** | 대본을 읽고 → 70점 이상 |
| S4 | 앱이 띄운 QR을 **라즈베리파이가 읽고 출금이 차단된다** | ATM 화면이 빨갛게 바뀌고 50만원을 눌러도 서보가 안 움직인다 |

**S4가 이 앱의 존재 이유입니다.** S1~S3은 거기까지 가기 위한 사다리입니다.

## 3. 범위

### 포함

- 로그인 (아이디/비밀번호 → 토큰 보관)
- **문자 공유 받기** (다른 앱에서 `공유` → 이 앱)
- **스피커폰 실시간 받아쓰기** (마이크 → 텍스트)
- 텍스트 직접 입력·수정 (받아쓰기가 틀렸을 때 고칠 수 있어야 함)
- 분석 요청 및 결과 표시 (등급 · 점수 · 탐지 근거)
- **QR 표시** (ATM 카메라가 읽을 수 있는 밝기·크기로)
- 서버 주소를 화면에서 바꾸기 (전시장에서 IP가 바뀝니다)

### 제외

- 회원가입, 비밀번호 변경 — 시연 계정을 그대로 씁니다
- 문자함 자동 읽기(`READ_SMS`) — 공유 인텐트로 충분합니다
- 통화 자동 녹음 — **안드로이드가 막아 놨습니다** (9-3 참고)
- 분석 이력, 알림, 다크 모드, 다국어

## 4. 사용자 시나리오

### 시나리오 A — 문자 (FR-A)

```
1. 어르신이 문자 앱에서 의심 문자를 길게 누른다
2. [공유] → [보이스피싱 검사]  선택
3. 앱이 열리면서 문자 내용이 이미 입력되어 있다
4. [검사하기]를 누른다
5. 결과가 뜬다 — 위험 100점, 근거 4개
6. 화면에 QR이 뜬다
7. 그 QR을 ATM 카메라에 비춘다 → 출금이 막힌다
```

### 시나리오 B — 통화 (FR-B)

```
1. 어르신이 의심스러운 전화를 받는다
2. 스피커폰으로 바꾸고, 앱에서 [통화 받아쓰기]를 누른다
3. 상대방 말이 화면에 글자로 쌓인다
4. 통화가 끝나면 [중지] → [검사하기]
5. 이하 시나리오 A의 5~7과 같다
```

> **왜 스피커폰인가**: 안드로이드 10부터 일반 앱은 통화 음성을 녹음할 수 없습니다.
> 스피커폰으로 나오는 소리는 **통화 스트림이 아니라 주변 소리**라서 제한을 받지
> 않습니다. 기술적 우회가 아니라, 이 제약 아래에서 가능한 유일하게 깔끔한 방법입니다.

## 5. 화면 명세

화면은 **네 개**면 충분합니다.

### 5-1. 설정 화면 (첫 실행 시 / 언제든 접근 가능)

| 항목 | 내용 |
|---|---|
| 서버 주소 | 입력란. 기본값 `http://192.168.0.x:8000`. **전시장에서 반드시 바뀝니다** |
| 아이디 / 비밀번호 | 기본값 `halmeoni` / 시연 비밀번호 |
| [연결 확인] | `GET /health` 를 불러 성공/실패를 보여 준다 |

> 서버 주소를 코드에 박아 넣지 마세요. 전시장에서 IP가 바뀔 때마다 APK를 다시
> 빌드하게 됩니다. **이것 하나가 전시 당일 가장 많은 시간을 아껴 줍니다.**

### 5-2. 입력 화면 (메인)

| 요소 | 동작 |
|---|---|
| 큰 텍스트 입력란 | 공유로 받은 문자나 받아쓰기 결과가 들어온다. **직접 고칠 수 있어야 한다** |
| [통화 받아쓰기 시작 / 중지] | 누르면 마이크가 켜지고 인식된 말이 입력란에 이어 붙는다 |
| [지우기] | 입력란을 비운다 |
| [검사하기] | 분석을 요청한다 |

### 5-3. 결과 화면

| 요소 | 내용 |
|---|---|
| 위험 등급 | `안전` / `주의` / **`위험`** — 색으로도 구분 (초록/노랑/빨강) |
| 점수 | 0~100 |
| 탐지 근거 | 목록 (예: 기관 사칭 표현 감지) |
| **QR** | **`CAUTION` · `DANGER`일 때만** 표시 (5-4 참고) |
| [다시 검사] | 입력 화면으로 돌아간다 |

### 5-4. QR 표시 — 가장 신경 써야 할 화면

ATM 카메라가 읽어야 하므로 **모양보다 인식률이 우선**입니다.

- QR을 **화면 폭의 70% 이상**으로 크게
- 배경은 **흰색**, QR은 검은색 (테마 색을 입히지 마세요)
- QR을 띄우는 동안 **화면 밝기를 최대로** 올리고, **화면 꺼짐을 막습니다**
- 여백(quiet zone)을 QR 주위에 충분히

> 이 네 가지를 지키지 않으면 전시장 조명 아래에서 인식이 들쭉날쭉해집니다.
> ATM 쪽은 640×480으로 초당 10장을 보므로, **휴대폰 화면이 어두운 것이
> 1순위 실패 원인**입니다.

## 6. API 계약

> 아래는 **실제 코드에서 확인한 값**입니다. 전체 규격은
> `docs/03_데이터-연동-규격.md`를 보세요.

### 공통

- 모든 성공 응답은 `{"data": ...}` 로 감싸여 옵니다
- 모든 실패 응답은 `{"detail": {"code": "...", "message": "..."}}` 입니다
- 사용자용 API는 `Authorization: Bearer <토큰>` 헤더가 필요합니다
- 토큰 유효 시간은 **12시간** — 전시 당일 아침에 한 번 로그인하면 종일 갑니다

### 6-1. 로그인

```http
POST /api/v1/auth/login
Content-Type: application/json

{"username": "halmeoni", "password": "<시연 비밀번호>"}
```

```jsonc
// 200 OK
{"data": {"access_token": "eyJ...", "token_type": "bearer"}}
// 401 — {"detail": {"code": "INVALID_CREDENTIALS", "message": "..."}}
```

### 6-2. 분석 요청 ← **이 앱의 핵심 호출**

```http
POST /api/v1/analysis
Authorization: Bearer <토큰>
Content-Type: application/json

{"message": "[검찰청] 귀하의 계좌가 범죄에 연루되어..."}
```

```jsonc
// 200 OK
{"data": {
  "analysis_id": 12,
  "risk_level": "DANGER",          // SAFE | CAUTION | DANGER
  "risk_score": 100,               // 0~100
  "reasons": ["기관 사칭 표현 감지", "범죄 연루 언급 감지"],
  "summary": "기관 사칭 표현 및 범죄 연루 언급 감지",
  "detected_at": "2026-09-20T05:12:33",
  "message_text": "...",
  "session_id": "VP-000012",       // QR에 넣을 값
  "atm_action": "BLOCK"            // ALLOW | VERIFY | BLOCK
}}
```

**`message`는 최대 2000자입니다.** 한국어 통화는 분당 200~300자 정도이므로
**5분이 넘는 통화 받아쓰기는 잘립니다.** 앱에서 글자 수를 표시하고, 넘치면
사용자가 줄일 수 있게 해 주세요.

### 6-3. QR에 넣을 값

**`session_id`만** 넣습니다. 위험 상세와 개인정보는 넣지 않습니다 — ATM이
서버에서 직접 조회합니다.

```json
{"session_id": "VP-000012"}
```

위 **JSON 문자열 그대로**를 QR로 만듭니다. 웹 프론트엔드가 쓰는 것과 같은
형식이고, 라즈베리파이는 이 형식만 정상으로 받습니다.

### 6-4. QR을 언제 띄우나

```
risk_level != "SAFE"  그리고  session_id != null   →  QR 표시
```

`SAFE`일 때는 QR을 띄우지 않습니다. 서버는 등급과 무관하게 `session_id`를
항상 만들지만, **평범한 문자는 시스템이 건드리지 않는다**는 것이 이 작품의
원칙입니다.

## 7. 안드로이드 기술 요구사항

| 항목 | 값 |
|---|---|
| 최소 SDK | API 26 (Android 8.0) — 시연 기기에 맞춰 조정 |
| 언어 | Kotlin (또는 Java) |
| UI | 기본 위젯 — 꾸미지 않습니다 |
| QR 생성 | ZXing (`com.google.zxing:core`) |
| 네트워크 | 표준 `HttpURLConnection` 또는 OkHttp |

### 7-1. 권한

| 권한 | 왜 |
|---|---|
| `INTERNET` | 백엔드 호출 |
| `RECORD_AUDIO` | 스피커폰 받아쓰기 |

**이게 전부입니다.** `READ_SMS`도 `WRITE_EXTERNAL_STORAGE`도 필요 없습니다.
권한이 적을수록 시연에서 설명하기 쉽고, 심사에서도 유리합니다.

### 7-2. 문자 공유 받기

`AndroidManifest.xml`의 메인 액티비티에 인텐트 필터를 추가합니다.

```xml
<intent-filter>
    <action android:name="android.intent.action.SEND" />
    <category android:name="android.intent.category.DEFAULT" />
    <data android:mimeType="text/plain" />
</intent-filter>
```

받는 쪽에서는 `intent.getStringExtra(Intent.EXTRA_TEXT)`로 꺼내
**입력란에 미리 채워 둡니다**(바로 분석하지 말 것 — 사용자가 확인하고
고칠 수 있어야 합니다).

### 7-3. 스피커폰 받아쓰기

안드로이드 기본 `SpeechRecognizer`를 씁니다. 클라우드 STT를 붙이지 않습니다.

- `RecognizerIntent.EXTRA_LANGUAGE`는 `ko-KR`
- `EXTRA_PARTIAL_RESULTS = true` — 말하는 도중에도 글자가 쌓여야 시연이 삽니다
- **`SpeechRecognizer`는 조용해지면 스스로 멈춥니다.** 통화는 중간에 말이
  끊기므로, `onEndOfSpeech` / `onError` 에서 **자동으로 다시 시작**해 주어야
  통화 전체를 받아쓸 수 있습니다. 이 재시작 처리가 이 앱에서 가장 까다로운 부분입니다
- 인식 결과는 **기존 텍스트에 이어 붙입니다**(덮어쓰지 않습니다)

## 9. 제약과 알려진 한계

**솔직하게 적어 둡니다. 전시 심사에서 질문받을 내용입니다.**

### 9-1. 에둘러 말하면 못 잡습니다

규칙 엔진은 키워드 사전 기반입니다. 실제로 넣어 본 결과입니다.

| 입력 | 점수 |
|---|---|
| "서울중앙지검 수사관입니다… 전액 인출하셔서 안전계좌로… 가족에게 말씀하지 마시고" | **100 (위험)** |
| "통장에 있는 거 좀 빼 오셔야 될 것 같은데, 누구한테 얘기하시면 안 되고요" | **0 (안전)** ⚠️ |

**전형적인 대본은 통화든 문자든 100점으로 걸립니다.** 하지만 구어체로
에둘러 말하면 놓칩니다. 시연 대본은 우리가 쓰므로 문제없지만,
*"즉흥으로 말해 보면요?"* 라는 질문에는 답을 준비해 두셔야 합니다.

→ 이것이 **외부 AI API를 붙이면 해결되는 영역**이고, PRD가 권하는 순서
(규칙 기반 완성 → AI 연결)의 이유이기도 합니다.

### 9-2. 받아쓰기는 100% 정확하지 않습니다

전시장은 시끄럽습니다. 그래서 **텍스트를 손으로 고칠 수 있어야 한다**는 것이
5-2의 요구사항입니다. 받아쓰기가 "검찰청"을 "거찰청"으로 옮기면 키워드가
안 걸립니다.

→ **백업 준비**: 시연용 통화 음성을 미리 녹음해 두고, 스피커로 틀면서
받아쓰는 방식을 준비해 두세요. 실시간 통화보다 훨씬 안정적입니다.

### 9-3. 통화를 앱이 직접 녹음할 수는 없습니다

안드로이드 10(API 29)부터 일반 앱의 통화 녹음이 차단됐습니다. 상대방 음성을
캡처하는 오디오 소스는 시스템 권한입니다. **"앱이 통화 버튼을 누르면 녹음 시작"
같은 구조는 만들 수 없습니다.** 스피커폰 방식이 이 제약에 대한 답입니다.

## 10. 개발 순서

**순서대로 하세요.** 각 단계마다 확인하고 다음으로 갑니다.

| 단계 | 하는 일 | 끝났다는 증거 |
|---|---|---|
| 1 | 설정 화면 + `/health` 연결 확인 | "연결됨"이 뜬다 |
| 2 | 로그인 → 토큰 보관 | 토큰을 받아 화면에 앞 10자를 찍어 본다 |
| 3 | 텍스트 입력 + 분석 요청 + 결과 표시 | 보이스피싱 문자를 붙여넣어 **100점**이 뜬다 (**S1**) |
| 4 | QR 표시 | ATM 카메라에 비춰 **출금이 막힌다** (**S4** — 여기가 고비) |
| 5 | 문자 공유 인텐트 | 문자 앱에서 공유해 3~4가 그대로 동작 (**S2**) |
| 6 | 스피커폰 받아쓰기 | 대본을 읽어 **70점 이상** (**S3**) |

4단계까지가 이 앱의 **80%**입니다. 5·6단계는 입력 방법을 늘리는 것뿐입니다.

> **1~4단계는 전화 기능이 전혀 필요 없습니다.** 문자를 붙여넣기만 해도 됩니다.
> 가장 어려운 검증(S4)을 가장 단순한 입력으로 먼저 끝내세요.

## 11. Flutter 담당 학생에게 넘길 것

이 앱이 끝나면 아래를 정리해 전달합니다. **이것이 이 앱의 최종 산출물입니다.**

1. **검증된 API 계약** — 6장에 실제 요청·응답 예시를 채워 넣은 것
2. **QR 인식이 잘 되는 조건** — 화면 밝기, QR 크기, 카메라와의 거리(실측값)
3. **받아쓰기 재시작 처리 방법** — 7-3에서 실제로 부딪힌 부분
4. **전시장에서 걸렸던 것들** — IP 변경, 무선 지연, 조명 등 실제 기록
5. **시연 대본** — 몇 점이 나오는지 확인된 문장들

Flutter 대응 패키지 참고 — `http`, `qr_flutter`, `speech_to_text`,
`receive_sharing_intent`. 구조는 같고 이름만 다릅니다.
