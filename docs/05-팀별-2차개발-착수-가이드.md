# 팀별 2차 개발 착수 가이드 (IoT 플랫폼 키트)

> 🧭 **2차 작업을 하는 중이라면 [00 · 2차 개발 통합 매뉴얼](00-2차개발-통합-매뉴얼.md)을 보세요.**
> 이 문서의 2차 작업 내용은 그 매뉴얼에 합쳐졌고, 여기는 착수 순서 원문으로 남겨 둡니다.

> 📂 **본편 05 / 팀 전원 / 2차 개발 시작하는 날** · 전체 목록 [docs/README.md](README.md)

이 문서는 **4개 팀(wakeup · classroom · study · subway)이 공통 키트 위에서 2차 개발을
시작할 때** 그날 무엇을 하는지 알려 줍니다. 규약 전문은 [부록F](부록F-IoT-개발-플랫폼-키트-규약.md)에
있고, 여기는 **실행 순서**만 담았습니다.

---

## 0. 한 장 요약 — 우리가 고치는 곳은 정해져 있습니다

| 하고 싶은 것 | 고치는 곳 | 고치지 않는 곳 |
|---|---|---|
| 부품 추가·제거·핀 변경 | `pi/slot_map.py` **한 줄** | `backend/` |
| 화면 디자인·시나리오(게임·미션) | `frontend/` | `backend/db/` |
| 반복 자동화(임계값·정해진 시각) | 코드 아님 — 대시보드 `/kit` 규칙 편집기 | `vision/main.py` |
| 카메라 감지 **대상** (사람·컵·책…) | 코드 아님 — 대시보드 `/kit` 영상인식 설정 | `vision/camera.py` |
| 카메라 감지 **방법** (손동작·자세…) | `vision/detectors/<우리팀>.py` **파일 하나** | `vision/detectors/base.py` |

> ⚠️ `backend/`·DB 스키마·`vision/` 공통 파일(`main.py`·`camera.py`·`detectors/base.py`·
> `detectors/__init__.py`·`detectors/objects.py`)을 고쳐야 할 것 같다면
> **먼저 멈추고 선생님께 물어보세요.** 대부분은 위 다섯 가지 중 하나로 해결됩니다.
> 정말 고쳐야 하는 경우라면 4팀 공통 사항이므로, 한 팀이 혼자 고치면 합칠 때 충돌합니다.
>
> 💡 감지 **방법**을 추가할 때도 백엔드와 대시보드는 고치지 않습니다.
> 검출기가 부팅할 때 자기 라벨을 서버에 신고하고, 설정 화면과 규칙 편집기가
> 그 신고를 보고 자동으로 채워집니다 (부록F 10장).

## 1. 팀 브랜치 만들기 (팀장 1명이 한 번만)

```bash
git fetch origin
git checkout -b classroom-v2 origin/platform    # 팀 이름으로
git push -u origin classroom-v2
```

브랜치 이름은 `wakeup-v2`, `classroom-v2`, `study-v2`, `subway-v2`로 통일합니다.

> **1차 완성본 브랜치(`wakeup` 등)는 지우지 마세요.** 우리가 만든 기록이고,
> 발표 자료에 쓰입니다. 2차 개발만 새 브랜치에서 합니다.

나머지 팀원은 그 브랜치를 받아옵니다.

```bash
git fetch origin && git checkout classroom-v2
```

## 2. 설치 (팀원 각자 자기 담당 폴더만)

[01 매뉴얼](01-학생용-설치-및-사용-매뉴얼.md) 1단계와 같습니다. 요약하면:

```bash
cd backend  && pip install -r requirements.txt   # 백엔드·DB 담당
cd frontend && npm install                       # 프론트엔드 담당
cd vision   && pip install -r requirements.txt   # 영상인식 담당
cd pi       && pip install -r requirements.txt   # 라즈베리파이 담당
```

`.env.example`을 각각 `.env`(프론트는 `.env.local`)로 복사하고 값을 채웁니다.
**`DEVICE_API_KEY`는 backend·pi·vision 세 곳이 똑같아야 합니다.**

## 3. 하드웨어 배치표 만들기 (라즈베리파이 담당)

우리 팀 예시를 복사한 뒤 **핀 번호만** 실제 배선에 맞게 고칩니다.

```bash
cd pi
cp examples/slot_map_classroom.py slot_map.py   # 자기 팀 파일로
python daemon.py --check                        # 핀 충돌·오타를 실행 전에 확인
python daemon.py                                # 실행
```

예시 파일은 [`pi/examples/`](../pi/examples/)에 팀별로 있습니다.
배치표를 고치고 데몬을 다시 실행하면 **대시보드에 카드가 자동으로 생기고 사라집니다.**

### 부품을 바꿀 때

| 상황 | 할 일 |
|---|---|
| 부품 추가 | `SLOTS`에 한 줄 추가 |
| 부품 제거 | 그 줄 삭제 (대시보드에서도 사라집니다) |
| 핀 변경 | `pin` 값만 수정 |
| 부저 종류 변경 | `buzzer_type`을 `passive` ↔ `active` |
| 버튼이 안 눌림 | `pull_up`을 반대로 |
| 키트에 없는 부품 | `drivers/`에 파일 하나 추가 (`apply`/`read` 2개 메서드) |

## 4. 화면과 시나리오 만들기 (프론트엔드 담당)

화면은 셋입니다.

| 주소 | 무엇 | 누가 고치나 |
|---|---|---|
| `/` | **우리 팀 화면** — 4팀 공통 출발점 | ★ 팀이 자유롭게 |
| `/kit` | 하드웨어 구성 · 자동화 규칙 · 영상인식 설정 | 키트 제공 (고치지 않아도 됨) |
| `/wakeup` | wakeup 팀 완성 화면 — **본보기** | 구조만 참고 |

우리 팀 화면은 `frontend/app/page.tsx`에서 시작합니다. 지금 상태로도 동작하며,
**"우리 팀 시나리오를 여기에 만듭니다"** 안내 카드가 자리를 표시해 둡니다.
슬롯 카드는 `<SlotGrid>` 한 줄이면 자동으로 그려지므로,
**부품이 바뀌어도 화면 코드는 그대로**입니다.

화면 제목은 코드가 아니라 `frontend/.env.local`에서 바꿉니다.

```env
NEXT_PUBLIC_TEAM_NAME=스마트 교실
NEXT_PUBLIC_TEAM_TAGLINE=사람이 들어오면 문이 열리고 조명이 켜집니다
```

### 시나리오(게임·미션) 작성

`useScenario()` 훅으로 씁니다. wakeup 팀의 기상 미션이 그대로 본보기입니다
(`frontend/scenarios/wakeupEngine.ts` = 판정 규칙, `useWakeup.ts` = 진행).

```tsx
const { slots, setActuator, onSensor, onVision, after, notify, serverTimer } = useScenario();

// 압력센서 값이 들어오면 혼잡도 LED 단계를 바꾼다
useEffect(() => onSensor("sensor_01", (e) => {
  const level = e.number! > 60 ? 3 : e.number! > 30 ? 2 : 1;
  void setActuator("actuator_01", "on", { level });
}), [onSensor, setActuator]);
```

**판정 규칙은 화면과 분리해서 쓰세요.** React 없이 순수 함수로 만들면
`node --experimental-strip-types`로 그대로 테스트할 수 있습니다
(wakeup의 `wakeupEngine.ts` + `wakeupEngine.test.ts` 참고).

> ⚠️ **브라우저 탭을 닫으면 시나리오가 멈춥니다.** 화면 없이도 일어나야 하는 것은
> 자동화 규칙이나 `serverTimer()`로 백엔드에 맡기세요 (부록F 9-3절).

## 5. 자동화와 감지 대상은 코드가 아닙니다

대시보드 `/kit`에서 바꿉니다. 코드를 고치거나 프로그램을 다시 켤 필요가 없습니다.

| 탭 | 무엇을 하나 |
|---|---|
| 하드웨어 구성 | 슬롯 20칸의 라벨·종류·사용 여부 |
| 자동화 규칙 | "온도가 28도를 넘으면 선풍기 켜기" 같은 반복 자동화 |
| 영상인식 설정 | 카메라가 무엇을 찾을지, 최소 신뢰도 |

규칙은 **브라우저를 닫아도 백엔드가 실행**합니다. 알람 예약도 규칙입니다.

## 6. 1차 완성본을 이미 올린 팀(wakeup)의 이행

백엔드가 DB를 열 때 **자동으로 옮깁니다.** 따로 할 일은 없지만, 무엇이 바뀌는지는 알아 두세요.

| 옛 것 | 새 것 |
|---|---|
| `buzzer_1` | `actuator_01` (라벨을 그대로 물려받음) |
| `touch_pad_1` | `sensor_01` |
| `camera_1` | 슬롯 없음 — `vision_events`로 들어옴 |
| `POST /api/alarm/schedule` | 자동화 규칙 (대시보드 알람 카드) |
| 백엔드 미션 엔진 | `frontend/scenarios/` |
| `pi/main.py` | `pi/daemon.py` + `pi/slot_map.py` |

옛 디바이스 행은 **지우지 않고 숨깁니다** — 우리가 쌓은 센서 기록과 제어 이력이
그 이름을 가리키고 있어서, 지우면 기록이 통째로 사라집니다.

## 7. 뭔가 안 될 때 — 먼저 돌려 보는 자가 점검

AI에게 묻기 전에 이것부터 돌리세요. 대부분 여기서 원인이 나옵니다.

```bash
cd backend  && python smoke_test.py              # 백엔드 기본 동작 (32항목)
cd backend  && python conformance_test.py        # 키트 약속이 지켜지는지 (69항목)
cd pi       && python daemon.py --check          # 배치표·배선·백엔드 주소
cd pi       && python test_slot_daemon.py        # 드라이버·부품 추가/제거 (39항목)
cd vision   && python test_vision_config.py      # 감지 설정·검출기 계층 (38항목)
cd pi       && python test_team_examples.py     # 팀별 배치표 예시 (32항목)
cd frontend && npx eslint . && npm run build     # 화면 코드
```

| 증상 | 먼저 볼 곳 |
|---|---|
| 대시보드에 부품이 하나도 없음 | 파이에서 `python daemon.py`를 실행했는지 |
| 카드는 보이는데 "반영 대기"에서 안 바뀜 | 파이 데몬이 켜져 있는지, `DEVICE_API_KEY`가 같은지 |
| 카메라가 엉뚱한 것을 감지 | `/kit` → 영상인식 설정에서 대상·신뢰도 조절 |
| 영상인식 설정에 검출기 목록이 비어 있음 | `python vision/main.py`를 한 번 켜야 신고가 올라갑니다 |
| 우리 검출기가 목록에 안 보임 | 파일에 `Detector` 클래스가 있는지, 이름이 `_`로 시작하지 않는지 |
| 카메라를 못 엶 | `CAMERA_SOURCE=usb` 또는 `picamera`로 지정해 보기 |
| 규칙을 만들었는데 동작 안 함 | 그 슬롯이 `enabled`인지, 규칙이 '켜짐'인지 |
| 소리가 안 남 | `slot_map.py`의 `buzzer_type`을 반대로 |

## 8. 키트가 업데이트되면 받아오기

```bash
git fetch origin
git merge origin/platform
```

충돌은 `frontend/`, `pi/slot_map.py`, `vision/detectors/<우리팀>.py`에서만 납니다 —
우리가 고친 곳이 거기뿐이기 때문입니다.
`backend/`나 `vision/` 공통 파일에서 충돌이 난다면 **우리가 고치면 안 되는 곳을 고친 것**이므로
그 변경을 되돌리고 0장의 방법으로 다시 해 보세요.

## 9. 지켜야 할 약속 (팀 간 합의)

1. 슬롯 ID(`sensor_01`~`actuator_10`)와 DB 스키마, API 응답 형식은 바꾸지 않습니다.
2. 팀 고유 부품 이름과 시나리오 라벨(게임·자세 이름)을 `backend/`와
   `vision/` 공통 파일에 넣지 않습니다. 팀 고유 감지는 `vision/detectors/` 안에만 둡니다.
   (`conformance_test.py`의 8번 검사가 잡아냅니다.)
3. 액추에이터의 `current_state`는 **하드웨어가 보고할 때만** 바뀝니다.
   백엔드가 직접 쓰면 배선이 빠져도 화면이 정상으로 보입니다.
4. 숫자 센서는 반드시 `{"value": 24.5}` 형식으로 보고합니다 — 그래야 차트가 자동으로 그려집니다.
5. 바꾼 뒤에는 7장의 자가 점검을 돌리고, 전부 통과한 상태로 커밋합니다.
